System design · L2R × Gupshup × WhatsApp

Qualifying after-hours leads on WhatsApp

When a lead lands in L2R outside the dealer's working hours, a templated WhatsApp message asks the customer when they plan to buy. If they pick two months or less, we move the lead to Qualification through the L2R API and ask them to pick a showroom visit date and time slot, so the sales executive starts the next morning with hot leads and booked visits. Every tap is tracked against the template that started the conversation.

Product lensEngineering lens

Problem and goals Product

A lead created at 12:26 AM (like the Tata Harrier EV inquiry assigned to Akshay) sits in First Call until the showroom opens. By then the customer has often enquired with two other dealers. Every lead also gets the same callback priority, whether the buyer is ready this fortnight or just browsing.

Customer problem

Gets no response at night, so they don't know if anyone saw the inquiry. Their intent goes cold.

Dealer problem

Sales executives start the day with an unsorted pile of overnight leads and spend the first calls on people who won't buy for months.

Goals

  • Respond to every non-working-hours (NWH) lead within a minute, with the dealer's name and the callback window.
  • Capture purchase timeline as structured data and auto-qualify leads with a timeline of two months or less.
  • Turn qualified leads into booked showroom visits (date from the next 7 open days, then a working-hours slot).
  • Give sales executives a prioritised morning queue, without changing how they work in L2R.
  • Measure engagement per template and per step, so template copy can be compared and improved.

Non-goals for v1

  • Free-text chatbot or LLM conversation. v1 uses buttons only.
  • Bot replies during working hours. Those leads go to a human caller as today.
  • Payments, finance or test-ride booking inside WhatsApp (see the roadmap).

The two-month threshold and the priority mapping live in dealer config, not code. Date and time lists come from the dealer's calendar: weekly offs and holidays are skipped, today is offered only if there are at least two working hours left, and WhatsApp lists hold at most 10 rows.

Which leads count as non-working hours

  • Each dealer has working hours per weekday, a timezone (default Asia/Kolkata), weekly offs and a holiday calendar.
  • A lead is NWH if lead.created_at falls outside those windows, including the last 15 minutes before close.

Who works where Product

L2R is the internal calling team's tool. Dealers work in a separate dealer panel. The OEM contract pays on conversion, so our team stays on the lead until it books.

There is one path to the dealer, and it belongs to L2R. A telecaller tags the follow-up form on a call, or the WhatsApp bot fills the same form fields through the L2R API. Either way, when the lead becomes qualified, L2R's event calls the dealer panel API. The bot never calls the dealer panel itself.

Why event-driven

L2R lead creation never waits on Gupshup. If Gupshup is down, leads still get created and sends retry from the outbox.

Why ack-then-process

The webhook only authenticates, stores the raw event and returns 200 in well under a second. Slow L2R calls happen in workers, so Gupshup never times out and retries.

Each outbound message (template or list) follows this lifecycle. Status events can arrive out of order, so transitions only move forward. A reply is accepted from any non-terminal state, and only for the step that message asked about. The 24-hour expiry applies to the template; an unanswered date or time list simply stays open.

Webhook processing Engineering

The reply processor runs these steps in order. Any failed check stops processing and is logged with a reason.

  1. Authenticate. Constant-time compare of the header token, plus a source IP check. Return 401 on failure.
  2. Persist and ack. Insert into wa_event with ON CONFLICT DO NOTHING, enqueue, return 200.
  3. Deduplicate. If the event ID was already processed, stop. This handles Gupshup retries and replays.
  4. Reject stale events. Skip if the timestamp is far outside the expected window. A late but genuine reply is logged for review.
  5. Map. Look up wa_message by context.gsId, then fall back to wamid, then to the lead ID in the postback.
  6. Cross-check. payload.source must equal the mapped row's mobile, and the template must be one we sent. A valid token alone can't qualify an unrelated lead.
  7. Check lead state in L2R. For the timeline answer, only change the stage if the lead is still in First Call. If a human already moved it on, add the answer as a comment only. The bot never downgrades a lead.
  8. Check the step. The postback's step must match the question that message asked, so an old date list can't be answered against the template.
  9. Record the tap in wa_interaction for tracking.
  10. Apply the rule for the step and option, using dealer config.
  11. Sync to L2R with an idempotency key (disposition, comment or visit), then send the next message in the flow.
def handle_reply(evt):
    if not wa_event.store(evt.id): return                     # dedupe
    pb  = parse_postback(evt.postback)                        # NWH_QUALIFIER|STEP|OPTION|LEAD
    msg = wa_message.find(gs_id=evt.context.gsId) or wa_message.find(wamid=evt.context.id) \
          or wa_message.find(lead_id=pb.lead_id)
    if msg is None:              return retry_later(evt)       # race with send
    if msg.mobile != evt.source: return reject("MOBILE_MISMATCH")
    if pb.step != msg.step:      return reject("STEP_MISMATCH") # answer must match the question
    wa_interaction.insert(evt.id, msg.gs_message_id, msg.lead_id, msg.root_template_id, pb.step, pb.option)
    outcome = rules.decide(pb.step, pb.option, dealer)        # QUALIFIED / NURTURE / DATE_CHOSEN / VISIT_BOOKED
    wa_message.record_reply(msg.id, pb.option, outcome)
    l2r_sync(msg, idempotency_key=f"wa-{evt.id}")             # dispose / comment / schedule visit
    send_next_step(msg, pb)                                   # date list → time list → confirmation

Webhook security Engineering

The callback is authenticated with a token. The token proves who sent the request. It does not prove the body wasn't altered or replayed, so we layer business checks on top.

Token hygiene

  • Send it in a header, not ?token=, which leaks into logs
  • Store it in a secrets manager
  • Compare in constant time
  • HTTPS only
  • Rotate with two valid tokens during switchover
  • Use one token per Gupshup app or dealer

Closing the gap

  • Allowlist Gupshup's published IP ranges
  • Deduplicate on message ID to block replays
  • Reject stale timestamps
  • Require the context ID to match a template we sent, and the sender to match the lead's mobile
  • Rate limit and alert on reply spikes
  • Move to HMAC body signing if Gupshup offers it

"The webhook is authenticated with a header token stored in a secrets manager and restricted to Gupshup IPs. Every event is validated against the message ID we sent and the lead's mobile number, so a leaked token alone can't qualify leads."

Compliance and cost Product

  • Opt-in. Meta requires consent before business-initiated messages. The lead form on CarWale and dealer sites should carry a WhatsApp consent line, stored with the lead. No consent, no template.
  • DPDP Act (India). Purpose-limited use of the mobile number, opt-out honoured, and retention limits on raw webhook payloads (for example, 90 days).
  • Template category. The message responds to the customer's own inquiry, so submit it as Utility. Meta may reclassify a question-style template as Marketing, which costs more and has stricter limits, so budget for both.
  • Cost control. One template per lead. The follow-up "Thanks" is a free-form session message inside the 24-hour window the customer opened by replying.
  • Number quality. Clear copy, dealer branding and an easy opt-out keep block rates low and protect the dealer's messaging tier.

Open questions

  • Which Gupshup API are we on (partner/self-serve or Enterprise)? The callback shape differs.
  • Does Gupshup support HMAC request signing, and does it publish stable IP ranges?
  • Does the L2R API support idempotency keys and a single call for dispose plus stage change, or two calls that need ordering?
  • Who owns dealer working hours today? Is there an existing calendar in L2R, or does this service hold it?
  • Is WhatsApp consent already captured on every lead source (CarWale, OEM site, walk-in, third-party portals)?
Sources: Gupshup docs on inbound messages, subscriptions and notifications, quick reply callbacks, and the partner template message API. The L2R API shapes are assumptions for this design.
